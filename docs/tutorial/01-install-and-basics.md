# Глава 01 — Установка Nix и базовые концепции

## Установка на обычный Linux (не NixOS)

У вас обычный дистрибутив (Ubuntu/Debian/Arch/...), и Nix ставится поверх него как обычный package manager, без замены системы. Есть два основных инсталлятора:

### Вариант A — официальный инсталлятор

```bash
sh <(curl -L https://nixos.org/nix/install) --daemon
```

Флаг `--daemon` ставит **multi-user** режим: появляется системный демон `nix-daemon`, отдельные системные пользователи `nixbld1..N` для сборок в песочнице, и все пользователи машины могут использовать общий store `/nix/store`. Это стандартный выбор для рабочей станции.

### Вариант B — Determinate Systems installer

```bash
curl --proto '=https' --tlsv1.2 -sSf -L https://install.determinate.systems/nix | sh -s -- install
```

Отличия: сразу включены flakes (см. ниже), более предсказуемое поведение при обновлениях, встроенная интеграция с Determinate Nix (опционально). Для целей этого tutorial функционально эквивалентен варианту A + включению flakes.

Выбирайте любой — дальнейшие главы не зависят от выбора инсталлятора. После установки перезапустите терминал (или `. /etc/profile.d/nix.sh`), затем проверьте:

```bash
nix --version
```

### Включение Flakes (если ставили вариант A)

Flakes и команда `nix` (без дефисов, `nix build`/`nix develop`/...) по умолчанию помечены experimental. Включите их в `~/.config/nix/nix.conf`:

```
experimental-features = nix-command flakes
```

Без этой строки все команды вида `nix build .#app`, использованные в этом tutorial, будут отказывать с ошибкой про experimental feature.

## Ключевые концепции

### Nix store

Всё, что Nix собирает или скачивает, попадает в `/nix/store/<hash>-<name>`, где `<hash>` — криптографический хеш от **всех входов**, повлиявших на результат (исходники, флаги компиляции, версии зависимостей, сам код сборки). Два разных набора входов → два разных пути в store, они никогда не перезатирают друг друга. Один и тот же набор входов → один и тот же hash → Nix может просто взять готовый результат из кеша, не пересобирая.

Отсюда следует главное: **путь в store — это одновременно и результат, и его точный "рецепт"**. Если вы видите `/nix/store/abc123...-libB-1.0`, то `abc123` детерминированно зависит от того, из какого именно коммита/патча/флагов собрана `libB`. Это прямо связано с темой override по веткам (глава 07) — сборка с custom-веткой и сборка с базовой веткой получат **разные** hash в store и будут существовать одновременно, не конфликтуя.

### Derivation

Derivation — это описание того, как получить некий output: какие входы, какая программа-builder, какие аргументы. Файлы `*.nix` не собирают ничего сами — они **описывают** derivations. Реальная сборка происходит, когда вы явно просите Nix реализовать (realize) derivation, например через `nix build`.

```bash
nix repl
```

```nix
:l <nixpkgs>
pkgs.hello
```

`pkgs.hello` — это derivation-значение (attribute set с полем `type = "derivation"`). Пока вы не запросили `nix build`, никакой компиляции не произошло — это просто описание.

### Purity / детерминированность

Сборка derivation происходит в **песочнице**: без сети (кроме fixed-output derivations, о которых в главе 03), с фиксированным набором переменных окружения, без доступа к произвольным файлам системы. Цель — чтобы результат зависел только от явно указанных входов, а не от того, что случайно установлено на конкретной машине. Это свойство и называют purity, и оно ровно то, что делает hash в store надёжным.

Отсюда и ограничение, важное для главы 07: **проверка "существует ли ветка X на GitLab" — это сетевой запрос**, а значит несовместим с чистой (pure) сборкой derivation. Именно поэтому branch-fallback логика не может быть частью самого `flake.nix`, вычисляемого в pure-режиме — придётся явно выходить за его границы (`--impure` или внешний скрипт).

### Garbage collection

Store растёт бесконечно, если не чистить. `nix-collect-garbage -d` удаляет всё, на что не ведут "живые" ссылки (GC roots — профили, результаты `nix build` в текущей директории через симлинк `./result`, и т.п.). Полезно знать заранее, чтобы не удивляться, куда пропал результат вчерашней сборки, если вы удалили симлинк `result` и почистили GC.

## Базовые команды, которые пригодятся дальше

```bash
nix repl                    # интерактивный eval nix-выражений — лучший инструмент для экспериментов с языком (глава 02)
nix build .#foo             # собрать output "foo" описанного в flake.nix текущей директории
nix develop                 # войти в devShell — окружение с нужными компиляторами/тулами в PATH
nix flake show               # показать, какие outputs объявляет flake
nix flake check               # прогнать проверки flake (в т.ч. что все системы evaluable)
nix why-depends <path> <dep> # почему в результат попала эта зависимость — полезно при разборе больших деревьев (глава 06)
nix path-info -S ./result   # размер store-пути и его closure
```

Классические (pre-flake) команды `nix-shell`, `nix-env`, `nix-build` тоже работают и вы будете встречать их в старых материалах/README сторонних проектов — они делают то же самое, но без `flake.lock` и без формального разделения `inputs`/`outputs`. В этом tutorial используем современный `nix` CLI + flakes как основной путь (глава 04), но полезно узнавать классический синтаксис при чтении чужого кода.

## Проверка себя

- Установите Nix, добейтесь, что `nix --version` и `nix repl` работают.
- В `nix repl` вычислите `1 + 2`, затем `builtins.currentSystem` — убедитесь, что получаете строку вида `x86_64-linux`.
- Запустите `nix-collect-garbage --dry-run` — прочитайте, что бы удалилось, ничего реально не удаляя.

Следующая глава — язык выражений Nix, без которого дальнейшие `flake.nix` будут просто "магическими текстами".
