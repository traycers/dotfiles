# Глава 02 — Язык выражений Nix

Nix-язык — это чистый, ленивый, функциональный язык **только для описания данных и функций**, которые потом интерпретирует Nix (сборка, установка пакетов). У него нет циклов, нет мутации переменных, нет побочных эффектов (кроме нескольких специально помеченных "impure" builtins). Всё — выражение, которое вычисляется в значение.

Открывайте `nix repl` и пробуйте каждый пример по ходу чтения — это быстрее, чем читать без проверки.

## Базовые типы

```nix
42                    # int
3.14                  # float
"hello"               # string
"multi ${"line"}"     # string interpolation — ${...} внутри строк
true / false          # bool
null                  # null
[ 1 2 "three" ]        # list — разнотипный, разделитель пробел, НЕ запятая
{ a = 1; b = "two"; } # attribute set (attrset) — главная структура данных Nix
```

Важно: списки разделяются **пробелом**, а не запятой — `[ 1 2 3 ]`, не `[1, 2, 3]`. Это частая ошибка у новичков.

## Attribute sets — основная структура

```nix
{ name = "app"; version = "1.0"; deps = [ "libB" ]; }
```

Доступ: `set.name`, `set.deps`. Вложенность: `{ a.b.c = 1; }` — синтаксический сахар для `{ a = { b = { c = 1; }; }; }`.

`rec` делает attrset "самоссылающимся" — поля видят друг друга:

```nix
rec {
  version = "1.0";
  name = "app-${version}";  # без rec тут была бы ошибка — version не виден
}
```

Это ровно тот механизм, которым в `mkDerivation { name = "..."; version = "..."; ... }` одно поле ссылается на другое.

## Функции

Любая функция Nix берёт **ровно один аргумент**. Функции нескольких аргументов — это функции, возвращающие функции (каррирование):

```nix
x: x + 1                     # функция от одного аргумента
x: y: x + y                  # функция от x, возвращающая функцию от y
(x: y: x + y) 2 3            # => 5, применение по очереди
```

### Аргумент-attrset (самый частый паттерн в nixpkgs)

```nix
{ pkgs, lib, ... }: pkgs.hello
```

Это функция, принимающая один аргумент — attrset, из которого сразу деструктурируются поля `pkgs` и `lib`. `...` разрешает attrset содержать и другие поля, которые эта функция игнорирует. Это ровно та форма, в которой написан **любой** `default.nix`/модуль пакета в nixpkgs, и она же будет в наших `flake.nix` при вызове `outputs = { self, nixpkgs, ... }: ...`.

Дефолтные значения и переименование при деструктуризации:

```nix
{ pkgs, buildType ? "release", src: mySrc }: ...
```

## `let ... in`

Локальные привязки, видимые друг другу (как `rec`, но для локального скоупа):

```nix
let
  x = 1;
  y = x + 1;
in x + y   # => 3
```

## `with`

Заносит все поля attrset в область видимости — удобно, но снижает читаемость (непонятно, откуда взялось имя), используйте умеренно:

```nix
with pkgs; [ cmake gcc gnumake ]
# эквивалентно [ pkgs.cmake pkgs.gcc pkgs.gnumake ]
```

## Ленивость (laziness)

Nix вычисляет значение только тогда, когда оно **реально нужно**, и только один раз (с мемоизацией через thunk). Это позволяет писать:

```nix
let
  a = b + 1;   # b ещё не определён на этой строке текстуально ниже — не важно
  b = 41;
in a           # => 42, всё ок, потому что порядок в let не важен благодаря ленивости
```

Практическое следствие: attrset с "битым" полем (ошибка вычисления) можно спокойно передавать и хранить — ошибка вылетит только при обращении к конкретному полю. Это то, за счёт чего в nixpkgs существуют тысячи пакетов, часть которых битая на некоторых платформах, но всё нормально до тех пор, пока вы не запросите именно эти пакеты.

## `import` — просто вызов функции

`import ./foo.nix` читает файл, вычисляет содержащееся там выражение и возвращает его значение. Если файл — функция, `import` вернёт функцию, которую нужно применить дальше:

```nix
# foo.nix
{ x, y }: x + y
```

```nix
# использование
import ./foo.nix { x = 1; y = 2; }   # => 3
```

Это ключевой момент: `default.nix` большинства пакетов в nixpkgs — это именно такой файл-функция, и `callPackage` (глава 08) — это просто удобный способ вызвать `import` с автоматическим заполнением аргументов из общего pkgs-набора.

## Строки, пути и интерполяция

```nix
./src              # тип `path`, относительно текущего файла, НЕ строка
"${./src}"         # приведение path к строке — Nix копирует путь в store и вставляет store-путь
"${pkgs.hello}/bin/hello"  # частый паттерн — получить путь к бинарнику внутри store-пути пакета
```

Важно понимать: когда path или derivation интерполируется в строку, Nix **добавляет его как зависимость** — то, что использовано таким образом, становится частью closure сборки.

## Множественная композиция attrsets

```nix
{ a = 1; } // { b = 2; }          # => { a = 1; b = 2; } — правый оператор перекрывает левый при конфликте ключей
lib.recursiveUpdate a b            # глубокое (рекурсивное) слияние, а не поверхностное //
```

`//` вам встретится в overlays и overrides постоянно — это буквально механизм "переопределения" на уровне attrset.

## Fixed-point паттерн — основа overlays

Это самая нетривиальная, но самая важная для дальнейшего идея. Посмотрите на функцию:

```nix
self: super: {
  myPkg = super.myPkg.overrideAttrs (old: { version = "2.0"; });
}
```

`self` — это "итоговый", уже полностью собранный набор пакетов (включая применённые оверлеи), `super` — набор пакетов **без** текущего оверлея (предыдущий слой). Функция `fix` в `lib` решает уравнение `self = f self`:

```nix
fix = f: let result = f result; in result;
```

Именно так `nixpkgs` строит финальный `pkgs`: применяет цепочку overlay-функций `self: super: {...}` через `fix`, каждая видит финальный результат (`self`, для ссылок на себя/другие пакеты после оверлея) и предыдущий слой (`super`, чтобы взять "старую" версию и модифицировать через `overrideAttrs`). Это выглядит как рекурсия "самого в себя", но благодаря ленивости Nix это работает: `self` — это thunk, который вычислится позже, а сейчас достаточно, что он существует как значение, на которое можно сослаться.

Понимание этого паттерна снимет ощущение "магии" с overlays в главе 08 — там это будет просто применение fixed-point к реальному `pkgs`.

## Практика

В `nix repl`:

```nix
:l <nixpkgs>
let f = self: super: { greeting = "hi, ${super.hello.pname}"; }; in (f { hello = pkgs.hello; } { hello = pkgs.hello; })
```

Попробуйте написать свою функцию с `rec`, с `let`, с деструктуризацией аргумента-attrset и с дефолтным значением — прежде чем переходить дальше. Следующая глава — `stdenv.mkDerivation`, где весь этот синтаксис уже применяется к реальной сборке C/C++ кода.
