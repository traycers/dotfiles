## Import From Derivation (IFD)

Иногда `.nix`-файл сборки хочет использовать **результат** одной derivation как **вход** для вычисления другой (например, сгенерировать список файлов через отдельный скрипт и `import` результат). Это называется IFD и требует пересечения evaluation-фазы и build-фазы, что медленнее обычного (Nix должен реально собрать промежуточный результат, чтобы продолжить evaluation). В большинстве C++ CMake-сценариев IFD не нужен — вы с ним встретитесь, если начнёте генерировать Nix-код из внешних манифестов (например, автоматически описывать все зависимости `vcpkg.json`/`conanfile.txt` через генератор).

## Кросс-компиляция C++

`nixpkgs` поддерживает кросс-компиляцию через `pkgsCross.<target>`:

```nix
pkgs.pkgsCross.aarch64-multiplatform.stdenv.mkDerivation { ... }
```

Здесь становится критичным разделение `nativeBuildInputs`/`buildInputs` из главы 03 — `nativeBuildInputs` (компилятор, cmake) остаются "для машины-сборщика" (host), `buildInputs` (библиотеки) собираются "для целевой платформы" (target). CMake-специфика: Nix автоматически подставляет `CMAKE_TOOLCHAIN_FILE` для кросс-случая через cmake setup-hook — вручную писать toolchain-файл, как в "чистом" CMake без Nix, обычно не требуется.

## Статическая линковка и санитайзеры

- Статическая линковка: `pkgsStatic.stdenv.mkDerivation` — весь closure собирается со статическими версиями библиотек (`*.a` вместо `*.so`), полезно для минимальных/portable бинарников.
- Санитайзеры (ASan/UBSan/TSan) — обычно через `cmakeFlags = [ "-DCMAKE_CXX_FLAGS=-fsanitize=address" ];` — Nix здесь не добавляет никакой особой магии, это стандартные CMake-флаги, просто прокинутые через `mkDerivation`.

## Remote builders

Если сборка требует другой архитектуры (например, вы на x86_64, а нужен `aarch64-linux`) или больше ресурсов, чем у локальной машины, Nix поддерживает делегирование сборки на другую машину через SSH (`nix.conf`: `builders = ssh://user@remote-machine x86_64-linux,aarch64-linux`). Это прозрачно для `flake.nix` — код сборки не меняется, меняется только то, **где** физически выполняется builder.

## `nix develop` + direnv

Ручной `nix develop` каждый раз при входе в директорию проекта — не самый удобный workflow. [direnv](https://direnv.net) + [nix-direnv](https://github.com/nix-community/nix-direnv) автоматически активируют `devShell` при `cd` в директорию с `.envrc`, содержащим `use flake`. Результат: открываете терминал/IDE в `examples/app` — `cmake`/`gcc`/`gdb` уже в `PATH`, без явного `nix develop`.

## `nix flake check`

Стандартный способ добавить тесты/проверки, запускаемые единой командой:

```nix
checks.${system}.unit-tests = pkgs.stdenv.mkDerivation {
  name = "app-tests";
  src = self;
  nativeBuildInputs = [ pkgs.cmake ];
  buildInputs = [ libB.packages.${system}.default ];
  doCheck = true;
  checkPhase = "ctest --output-on-failure";
  installPhase = "touch $out";  # checks обычно не производят полезный output, только факт успеха
};
```

`nix flake check` соберёт все `checks.*` и завалится, если хоть один упал — естественная точка для CI (глава 09) вставить полноценный gate до `nix build` продакшен-артефакта.

## Отладка неудачных сборок

- `nix log <store-path>` — полный лог конкретной сборки, даже если она давно завершилась (если не была собрана GC).
- `nix build --keep-failed` — не удаляет временную директорию сборки при ошибке, что позволяет зайти в неё руками и разобраться, почему `cmake`/`make` упал именно в песочнице (частая причина — недостающий `buildInput`, который "случайно" был доступен в обычной, не-sandboxed среде разработчика).
- `nix build --print-build-logs` (или `-L`) — стримит лог сборки в реальном времени, а не только при ошибке.

## Куда читать дальше

- Nix Pills — подробно про механику derivations "снизу", если хочется понять `builtins.derivation` до последней детали.
- Руководство nixpkgs (`nixos.org/manual/nixpkgs`) — полный список доступных `stdenv`-хуков, `lib`-функций, готовых builder-ов (`buildGoModule`, `buildRustPackage`, аналоги для других языков — полезно, если ваше дерево не чисто C++).
- Обсуждения flakes RFC — если хочется понять, почему flakes до сих пор "experimental feature" спустя несколько лет, и какие альтернативы (`flake-parts`, `devenv`) существуют для структурирования больших flake-репозиториев.
