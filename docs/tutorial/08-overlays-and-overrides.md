# Глава 08 — `overrideAttrs`, `.override`, overlays, `callPackage`

Глава 07 решала вопрос "из какой **ветки/источника** собирать". Эта глава — про другой, часто путаемый с ним вопрос: "как изменить **параметры** уже существующего пакета" (версию, флаги компиляции, патчи, зависимости) без правки его исходного `.nix`-файла. Оба механизма можно комбинировать (например, override исходника по ветке **и** override флагов сборки одновременно), но это разные инструменты.

## `callPackage` — как `import`, но с автоподстановкой аргументов

Из главы 02: `import ./foo.nix` возвращает функцию, если файл — функция, и вам нужно вызвать её руками с аргументами. `callPackage` делает это автоматически, беря аргументы с совпадающими именами из общего `pkgs`:

```nix
# libC.nix
{ stdenv, cmake }:
stdenv.mkDerivation { pname = "libC"; ... nativeBuildInputs = [ cmake ]; }
```

```nix
pkgs.callPackage ./libC.nix { }
# эквивалентно: import ./libC.nix { stdenv = pkgs.stdenv; cmake = pkgs.cmake; }
```

`callPackage` смотрит на имена параметров функции (`stdenv`, `cmake`) и берёт их из `pkgs` автоматически. Второй аргумент — attrset **явных переопределений** аргументов (например, если вы хотите передать не `pkgs.cmake`, а какой-то другой `cmake`).

## `.override` — заменить входные аргументы derivation

Каждый пакет, полученный через `callPackage`, автоматически получает атрибут `.override` — функцию, которая повторно вызывает исходную функцию-пакет с изменёнными аргументами:

```nix
myLibB = pkgs.callPackage ./libB.nix { };

myLibB.override (old: {
  # переопределяем САМ АРГУМЕНТ libC, который получила функция пакета libB.nix
  libC = myLibB.libC.overrideAttrs (o: { patches = [ ./fix.patch ]; });
})
```

`.override` работает на уровне **аргументов функции**, а не на уровне готовой derivation — то есть это как если бы вы вызвали `callPackage` заново с другими входами. Полезно, когда нужно подставить другую версию **зависимости**.

## `.overrideAttrs` — изменить атрибуты самой derivation

```nix
pkgs.hello.overrideAttrs (oldAttrs: {
  version = "2.12.2";
  src = pkgs.fetchurl {
    url = "mirror://gnu/hello/hello-2.12.2.tar.gz";
    sha256 = "...";
  };
  patches = (oldAttrs.patches or []) ++ [ ./my-patch.patch ];
})
```

`overrideAttrs` берёт функцию `oldAttrs: { ... }`, где `oldAttrs` — итоговый attrset, переданный в `mkDerivation` **до** переопределения, и возвращает **новый** attrset, слитый через `//` с изменениями. Это самый частый инструмент "точечно изменить одну готовую сборку" — например, накатить патч на версию библиотеки из nixpkgs без форка всего дерева.

**Связь с главой 07**: если бы вы вместо честного дерева flake-inputs использовали единый `nixpkgs`-стиль с одной версией всех библиотек, "переключение на custom-ветку" можно было бы реализовать через `overrideAttrs`, заменив `src` на нужный `fetchGit`. Но для дерева из **независимых** git-репозиториев (ваш кейс) естественнее управлять источником через flake `inputs`/`--override-input` (глава 07), а `overrideAttrs` оставить для более локальных правок (флаги компилятора, патчи, версии транзитивных зависимостей внутри nixpkgs).

## Overlays — системное применение `overrideAttrs`/`.override` ко всему набору пакетов

Из главы 02 (fixed-point): overlay — функция `self: super: { ... }`, применяемая к целому `pkgs`:

```nix
overlay = self: super: {
  libB = super.libB.overrideAttrs (old: {
    cmakeFlags = (old.cmakeFlags or []) ++ [ "-DENABLE_FEATURE_X=ON" ];
  });
};

pkgs = import nixpkgs { overlays = [ overlay ]; system = "x86_64-linux"; };
```

Overlay полезен, когда изменение должно применяться **везде**, где используется `pkgs.libB` в большом дереве (в отличие от `.override`/`.overrideAttrs`, которые меняют одну конкретную ссылку на пакет). В контексте вашего дерева `app/libB/libC` через отдельные flakes overlays не обязательны — управление версиями идёт через `inputs`/`follows` (глава 06), а overlays чаще нужны, когда вы патчите что-то **из общего `nixpkgs`** (например, зафиксировать другую версию `boost` для всего дерева).

## Когда что использовать — практическая шпаргалка

| Задача | Инструмент |
|---|---|
| Собрать из другой ветки/репозитория целиком | `flake inputs` + `--override-input` (глава 07) |
| Добавить патч/флаг компиляции к одной сборке | `.overrideAttrs` |
| Подставить другую версию зависимости в один конкретный пакет | `.override` |
| Изменить пакет системно везде, где он используется через общий `pkgs` | overlay |
| Вызвать `.nix`-файл-функцию с автоподстановкой `pkgs`-аргументов | `callPackage` |

## Проверка себя

- Напишите overlay, который добавляет `-DCMAKE_BUILD_TYPE=Debug` в `cmakeFlags` вашей `libC` из `examples/libC`, не трогая её `flake.nix`.
- Объясните разницу между `.override` и `.overrideAttrs` своими словами — какая изменяет входы функции-пакета, а какая — итоговый attrset derivation.
- Объясните, почему branch-fallback (глава 07) плохо ложится на `overrideAttrs`, если у вас дерево из отдельных git-репозиториев с собственными `flake.lock`, а не единый набор пакетов внутри одного nixpkgs-подобного репозитория.
